# Правила разработки Structura

Применяются ко всему проекту, включая core, render, edit, инструменты и тесты.

- Не добавлять комментарии в код. Объяснения архитектуры и решений хранить в Markdown-документации.
- Писать понятный, читаемый и компактный код. Использовать точные имена, явные зависимости и простой поток выполнения.
- Сокращать дублирование и лишнюю сложность, сохраняя читаемость. Не уплотнять код в трудные для понимания однострочники.
- Разделять обязанности: core — данные и форматы, render — графика, edit — операции редактирования и интерфейс. Логика библиотеки не зависит от GUI.
- Не наращивать монолитные модули и функции. Если изменение затрагивает несколько обязанностей, сначала выделить связные части с явными интерфейсами. Размер файла служит сигналом для проверки, а не поводом дробить код механически; не заменять монолит цепочкой обёрток, mixin-классов или циклических импортов.
- Выбирать стандартные возможности языка и используемых библиотек. Добавлять абстракции для существующих задач; расширять через небольшие ясные интерфейсы.
- Хранить общую логику, параметры и значения по умолчанию в одном месте. GUI и Python API используют одни операции.
- Держать интерфейс отзывчивым: тяжёлые вычисления и I/O выполнять вне потока GUI, обновлять только затронутые данные, ограничивать очереди и кэши.
- Проверять производительность измерениями. Оптимизировать подтверждённые узкие места, сохраняя корректность и ясность реализации.
- Делать изменения последовательно и по делу. Проверять существенное поведение подходящими тестами; поддерживать документацию в соответствии с реализацией.
